# 生成规范的共用步骤

每个规范 skill 都按这里的步骤执行。本次对话里 `init-standards` 已经完成第 1、2 步并经用户确认时，直接使用确认过的结果，不再重复识别和提问。

## 1. 确定目标项目和输出位置

- 目标项目默认是当前工作目录；用户给了别的路径就用那个路径。
- 规范文件写到 `<目标项目>/docs/standards/`，CLAUDE.md 写到目标项目根目录。
- 项目里已有别的规范目录（如 `doc/规范/`、`docs/conventions/`）时，问用户沿用哪个目录。

## 2. 识别技术

有代码就读代码推断；空项目或推断不出的项，问用户。

**读代码**，每条结论都记下依据的文件：

- 依赖与构建文件：`pom.xml`、`build.gradle*`、`go.mod`、`pyproject.toml`、`requirements*.txt`、`package.json`、`composer.json`、`*.csproj`、`Cargo.toml`。锁文件决定包管理工具：`pnpm-lock.yaml` 对应 pnpm，`yarn.lock` 对应 yarn，`package-lock.json` 对应 npm，`uv.lock` 对应 uv，`poetry.lock` 对应 Poetry。
- 工具配置：格式化、lint、类型检查、测试框架的配置文件，例如 `eslint.config.*`、`.eslintrc*`、`.prettierrc*`、`ruff.toml`、`checkstyle.xml`、`.golangci.yml`、`tsconfig.json`、`vitest.config.*`、`jest.config.*`、`.editorconfig`。
- 目录结构：前后端各自的源码根目录和分层方式。
- 现有写法：每层抽查 3 到 5 个文件，看命名、接口响应格式、错误处理、请求封装；数据库看迁移脚本或实体类（表名前缀、主键、通用字段、软删除）。
- 已有文档：`CLAUDE.md`、`AGENTS.md`、`README*`、`CONTRIBUTING*`、`docs/` 下的文档。
- 提交历史和仓库：`git log --oneline -30` 看提交说明的格式，`git branch -a` 看主分支名，`git remote -v` 看代码托管平台；CI 配置（`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile`）看 CI 里跑了哪些命令。

识别出的技术和版本写进技术选型规范 `docs/standards/tech-stack.md`，其他规范只写技术名，不重复写版本号。本次不生成技术选型规范、项目里也没有时，版本写在后端、数据库、前端规范的标题里；UI 设计规范的标题不写版本。

**提问**：只问下面两类问题，一次列给用户，每个问题附推荐值：

1. **会明显改变规则的选择**：答案会改动多条规则，而且几种做法都常见。例如接口 JSON 字段用 snake_case 还是 camelCase；界面类型（后台管理、面向用户的站点、移动端）；代码里同一件事有几种写法时以哪种为准；默认规则在目标技术里没有对应做法时选哪个方案（如 MySQL 软删除表的唯一约束）。
2. **没有可靠推荐值、只能由用户提供的取值**：项目名、业务域划分、部署方式和备份存放位置、代码托管平台（决定 CI 配置文件的位置，`git remote -v` 能看出来的不问）。

项目必然需要的能力直接写进规范，不当作问题：Web 前端的浅色/深色/跟随系统主题切换、窄屏下可用的响应式布局、后端的健康检查接口、依赖漏洞扫描、密码哈希等安全基线。

UI 的主题色、字号、间距这类视觉取值不提问，规范里写占位 `<待补充>`，由用户后续补充。

其余项一律直接用推荐值，不问：工具和版本、目录名、命名后缀、错误码分段、各种阈值、测试框架、备份时间和保留份数、分支命名、合并方式、评审人数、token 有效期等。推荐值取自对应 skill 的 `references/defaults.md`，已按目标技术改写。用了哪些推荐值，在汇报的"使用的推荐值"一节逐项列出，用户想改可以再提。

问题总数控制在 8 个以内，超过时只留影响最大的几个，其余按推荐值处理。用户在请求里已经回答的项不再问。用户说了"都用推荐值""不用问"时不提问：第 1 类直接用推荐值；第 2 类用户没给的，规范里写占位（例如 `<备份目录>`），并在汇报里列为"需要用户补充的取值"。

## 3. 确定每条规则的取值

按下面的优先级决定：

1. 用户在本次对话里明确说的。
2. 目标项目代码里已经统一使用的写法。例如所有表都用 `created_at`，规范就写 `created_at`，不改成默认的 `create_time`。
3. `references/defaults.md` 的默认规则，按目标项目的技术改写成对应写法。

下面几种情况按第 2 步的提问规则处理，不能不告诉用户就自己选：

- 代码里同一件事有两种以上写法，而且数量接近。例如一半接口返回统一响应、一半直接返回数据。
- 默认规则在目标技术里没有对应做法。例如 MySQL 没有部分唯一索引，软删除表的唯一约束要换方案。
- 项目名、业务域、部署方式这类只能由用户提供的取值，代码里找不到。

**禁止编造**：规范里出现的命令、路径、文件名、工具配置，要么在项目里真实存在，要么用户已经确认要新增。项目里还没有配置的工具（例如还没装 ESLint），规范里照常写规则，同时在汇报里列为"需要新增的配置"，不能写成已经在用。

## 4. 已有文件的处理

目标文件已经存在时：

1. 读完整个文件。
2. 和准备生成的内容逐条比较，分三类列给用户：
   - 新增：已有文件里没有的规则。
   - 冲突：同一件事规定不同，写出已有写法和新写法。
   - 相同：只给数量，不列条目。
3. 用户确认每个冲突项之后再写入：保留已有文件的章节顺序和措辞，把新增规则放进对应章节，冲突项按用户的选择修改。
4. 用户确认之前不写文件。

## 5. 写作要求

生成的文档给团队里的开发者和 AI 编程助手看：

- 中文书写，术语、命令、标识符保留英文原名。
- 每条规则一句话说清楚。硬性规则用 **必须** / **禁止** 开头；有例外的紧跟着写 **例外**，并写明适用范围。
- 命名类规则用表格（对象 | 规则 | 示例），示例用符合目标项目业务的名字。
- 能由工具检查的规则，写上检查它的工具和命令。
- 需要理由的规则，在条目下用一两句话写理由，不展开长篇解释。
- 用日常词汇，不用"落地""对齐""抓手""赋能"之类的说法。
- 文档只写目标项目自己的规定，不写参考了哪个项目或哪份外部规范（基线标准除外，例如 PEP 8、Effective Go）。
- 只写目标项目用得到的规则：项目里没有的东西（例如没有文件上传就不写附件存储），对应条目不写。

## 6. 写完后的检查

- 用 Grep 或 Glob 核对文档里出现的每个路径、命令、配置文件名在项目中存在；不存在的必须已在汇报里列为"需要新增的配置"。
- 检查没有残留其他技术的写法，例如 Java 项目的规范里不能出现 `pytest`、`ruff`，Vue 项目的规范里不能出现 `useEffect`、`JSX`。
- 检查多份规范之间一致：接口 JSON 字段的大小写、统一响应结构、分页参数、枚举值，在后端、前端、数据库规范中写法相同。
- 检查每件事只写在一处：版本号只在 `tech-stack.md`，提交说明格式只在 `workflow.md`，其他文件引用它们（对应文件本次没有生成时除外）。
- 向用户汇报：
  - 写了哪些文件；
  - 哪些规则来自代码推断，附依据的文件；
  - 使用的推荐值：没问用户、直接采用推荐值的项，每项一行"项目：取值"；
  - 需要新增的配置和需要用户后续补充的取值。
