# 生成 UI 设计规范

1. 读本 skill 目录往上两级的 `shared/workflow.md`（即插件根目录下的 `shared/workflow.md`），按其中的步骤执行。
2. 读本 skill 的 `references/defaults.md`。
3. 有代码时读下面这些位置，按读到的内容填写对应章节，每个组件和页面都写出源码路径：
   - 主题文件：CSS 变量文件（`globals.css`、`variables.scss`）、Tailwind 的 `@theme` 或 `tailwind.config.*`、组件库主题配置（Element Plus 的 `--el-*` 变量、Ant Design 的 `ConfigProvider theme`）→ 第 1 部分。
   - 组件目录（例如 `components/ui/`、`components/common/`、`components/app/`）→ 第 2 部分；变体和尺寸取组件源码里定义的取值。
   - 路由表、菜单配置和页面目录 → 第 3 部分；页面源码和请求函数 → 第 4 部分。页面多于 30 个时，第 4.2 节按菜单分组各写一张表。

   没有的写 `<待补充>`。只写代码里已有的组件和页面，不为空缺处设计新组件或新页面。
4. 主题切换（浅色、深色、跟随系统）和响应式是必须有的，直接写进规范，不询问用户。界面类型（后台管理、面向用户的站点、移动端）属于第 1 类问题，推荐值是"后台管理"；不是后台管理时，第 3 部分按实际界面类型改写，并在汇报里说明。
5. 输出 `docs/standards/design.md`；目标项目已有 `docs/standards/ui.md` 时沿用 `ui.md` 这个文件名，按 `shared/workflow.md` 第 4 步合并，不另建 `design.md`。下文的 `design.md` 都指实际使用的文件名。标题固定为 `# UI 设计规范`，不写版本号。章节为：1. 视觉风格　2. 控件组件规格　3. 页面结构　4. 页面逻辑，小节按 `references/defaults.md` 编号。开头写明："本文的变量全部定义在 <主题文件>，**禁止**在组件里写死颜色值或像素值。标 `<待补充>` 的内容由团队后续补充。技术约束以前端规范为准。"
6. 与前端规范分工：本文写界面看起来什么样、用户操作后发生什么；目录、命名、状态管理、请求层的写法只写在前端规范里，本文需要时写"见前端规范"。前端规范已存在时先读它，组件位置和目录名按它写。
7. 汇报里单独写两项：
   - "需要用户补充的取值"：列出所有 `<待补充>` 的内容，按四个部分分组。用户给了品牌色的，写明已填入主色，以及它和主色上文字的对比度是否达到 4.5:1。
   - 有代码时写"覆盖的组件和页面"：列出写进本文的组件和页面，以及代码和默认规则不一致、需要用户确认的地方。
