# 数据库规范默认规则

每章分"默认规则"和"按技术确定"两部分。默认规则以 PostgreSQL 的写法给出，目标数据库不同时换成对应写法；没有对应做法的，按"按技术确定"里的说明处理或问用户。

## 1. 命名

默认规则：
- **必须**：表名和字段名只用小写字母、数字和下划线（snake_case），以字母开头。
- **禁止**：名称中出现中文、空格、`-`、`#`、`@`，或使用驼峰写法。
- **必须**：表名加业务域前缀，用表格登记"前缀 | 业务域 | 表"。系统基础表用 `sys_`（用户、角色、权限、文件、操作日志、任务）。新增业务域时先在表里登记前缀。
- **必须**：特殊用途的表用统一后缀：多对多关系表 `_rel`，只追加不修改的日志表 `_log`，历史快照表 `_history`，配置表 `_config`。
- **禁止**：表名和字段名使用 SQL 保留字，例如 `user`、`order`、`group`、`desc`、`limit`、`offset`、`end`。遇到时换成更具体的名字：`desc` 改为 `step_desc`，`end` 改为 `end_time`，`order` 表改为 `<前缀>_order`。
- **禁止**：自造缩写，例如 `uid`、`amt`、`cnt`；只允许 `id` 这类通用缩写。
- **必须**：同一含义的字段在所有表中同名：
  - 外键写成 `<实体>_id`，例如 `order_id`。
  - 布尔字段以 `is_` 开头，例如 `is_enabled`。
  - 时间字段以 `_time` 结尾，例如 `paid_time`。
  - 只有日期的字段用日期类型、以 `_date` 结尾，例如 `begin_date`。
  - 操作人字段以 `_by` 结尾，例如 `approved_by`。
- **禁止**：表名里用"数据""信息""记录表"这类没有区分度的词，例如 `user_info_table`。

按技术确定：业务域和前缀（有表的项目按现有表名整理，空项目问用户有哪些业务域）；Oracle 等对象名默认大写的数据库，说明建表时不加引号、实际存储为大写。

## 2. 主键

默认规则：
- **必须**：每张表的主键都是名为 `id` 的 64 位整数，由数据库自增生成。写出建表写法和 ORM 写法。
- **禁止**：雪花 ID 这类长 ID、UUID 主键、字符串主键、用业务字段（编号、邮箱）做主键。
- **禁止**：在应用代码里生成主键。
- 理由（写进规范）：自增 ID 短而有序，对 B-tree 索引友好，可以直接作为编号给人看；数值远小于 2^53，前端 JavaScript 能精确表示，不会像 19 位雪花 ID 那样丢失精度。需要对外暴露不可猜测的标识（例如分享链接、API Key）时，另设字段存储。

按技术确定：
- PostgreSQL：`id BIGINT GENERATED ALWAYS AS IDENTITY`；MySQL：`id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`；SQL Server：`id BIGINT IDENTITY(1,1)`；Oracle 12c+：`id NUMBER(19) GENERATED ALWAYS AS IDENTITY`。
- ORM 写法：SQLAlchemy `mapped_column(BigInteger, Identity(always=True), primary_key=True)`；MyBatis-Plus `@TableId(type = IdType.AUTO)`；JPA `@GeneratedValue(strategy = GenerationType.IDENTITY)`；GORM `ID uint64 gorm:"primaryKey;autoIncrement"`。
- 项目是多库分片或多地写入时，自增主键不适用，停下来问用户。代码里已经统一使用雪花 ID 的，沿用并删掉"禁止雪花 ID"一条，理由改为说明前端要把 ID 当字符串处理。

## 3. 通用字段

默认规则：
- **必须**：业务表都包含下列字段，按这个顺序放在表的最后：

  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `create_by` | 64 位整数 | 创建人 ID；系统自动创建的记录为空 |
  | `create_time` | 带时区时间戳，非空，默认当前时间 | 创建时间 |
  | `update_by` | 64 位整数 | 最后修改人 ID |
  | `update_time` | 带时区时间戳，非空，默认当前时间 | 最后修改时间，更新时由应用层写入 |
  | `del_flag` | 小整数，非空，默认 0 | 软删除标记：0 未删除，1 已删除 |

- `_log` 表只追加不修改，只有 `create_by`、`create_time`；**禁止**对它执行 update 或 delete。
- `_rel` 关系表只需要 `create_by`、`create_time`，解除关系时直接物理删除。
- **禁止**：业务表执行物理删除。删除一律把 `del_flag` 置为 1，查询默认带 `del_flag = 0` 条件。

按技术确定：时间类型（PostgreSQL `TIMESTAMPTZ`；MySQL 没有带时区的时间类型，用 `DATETIME(3)` 统一存 UTC，并在连接参数里固定时区；SQL Server `DATETIMEOFFSET`）；ORM 的自动填充写法（MyBatis-Plus `MetaObjectHandler`、JPA `@CreatedDate`）和逻辑删除配置（MyBatis-Plus `@TableLogic`）。代码里已有统一的通用字段名（如 `created_at`、`deleted`）时沿用。

## 4. 字段类型

默认规则：用表格写"场景 | 必须使用 | 禁止"：

| 场景 | 必须使用 | 禁止 |
|---|---|---|
| 主键、外键 | 64 位整数 | 32 位整数、字符串 |
| 时间 | 带时区时间戳（存 UTC）；只有日期用日期类型 | 不带时区的时间戳、字符串 |
| 枚举或状态 | 短字符串 + `CHECK` 约束，存英文值，例如 `'active'` | 用魔法数字表示状态（本身就是等级数值的字段除外，例如优先级 1～4） |
| 布尔 | 布尔类型 | `CHAR(1)`、`'Y'`/`'N'` |
| 短文本 | `VARCHAR(n)`，n 按实际估算，例如名称 100、标题 255 | 一律写成 `VARCHAR(255)` |
| 长文本 | `TEXT` | — |
| 结构化扩展数据 | 数据库的 JSON 类型 | 在文本字段里存 JSON 字符串 |
| 金额 | `NUMERIC(18,2)` | 浮点类型 |
| 其他小数（数量、比例） | `NUMERIC(p,s)`，精度按业务定 | `FLOAT`、`DOUBLE`、`REAL` |

- **禁止**（PostgreSQL）：`char(n)`、`money`、`serial` / `bigserial` 类型；时间字段声明精度（如 `timestamptz(0)`）；`timetz` 类型和 `CURRENT_TIME` 函数。
- **禁止**：在数据库里存文件本体，文件放对象存储或文件服务，库里只存对象键（项目没有文件存储时删掉本条）。
- **禁止**：为"以后可能用到"预留字段。

按技术确定：MySQL 的布尔用 `TINYINT(1)`（MySQL 的 `BOOLEAN` 就是它），JSON 用 `JSON`，`CHECK` 约束要求 8.0.16 及以上（更低版本问用户改用应用层校验还是字典表）；PostgreSQL JSON 用 `JSONB`；SQL Server 布尔用 `BIT`，JSON 存 `NVARCHAR(MAX)` + `ISJSON` 检查。

## 5. 注释

默认规则：
- **必须**：每张表、每个字段都写中文注释。写出 ORM 或迁移工具里的写法。
- **必须**：注释按"业务含义。取值：…。约束"的格式写，例如：`订单状态。取值：pending-待支付，paid-已支付，cancelled-已取消。非空。`

按技术确定：PostgreSQL `COMMENT ON`；MySQL 建表语句里的 `COMMENT '...'`；SQLAlchemy `comment=`；JPA 无原生支持时写在迁移脚本里。

## 6. 字段顺序

主键 → 外键 → 核心业务字段 → 状态和分类字段 → 通用字段（第 3 节）。

## 7. 约束与索引

默认规则：
- **必须**：外键字段声明外键约束，删除行为用 `RESTRICT`（业务表是软删除，不做级联）。
- **必须**：每个外键字段都建索引。
- **必须**：带软删除的表，唯一性只约束未删除的行。
- **必须**：业务上唯一的字段（包括组合字段，例如"仓库 + 商品"）建唯一索引，**禁止**只靠应用层先查后插来保证唯一。
- **必须**：非空字段显式声明 `NOT NULL`；有默认值的字段写明 `DEFAULT`。
- **必须**：单表索引不超过 15 个（含主键和唯一索引）。
- **必须**：约束和索引按下表命名，能在 ORM 里统一配置命名规则的就统一配置，不手写名字：

  | 类型 | 格式 |
  |---|---|
  | 主键 | `pk_<表>` |
  | 外键 | `fk_<表>_<列>_<被引用表>` |
  | 唯一 | `uk_<表>_<列>` |
  | 普通索引 | `idx_<表>_<列>` |
  | 检查约束 | `ck_<表>_<名称>` |

- **禁止**：为没有查询场景的字段建索引。新加索引时在合并请求里写明对应的查询。

按技术确定：
- 软删除表的唯一约束：PostgreSQL、SQL Server 用部分唯一索引（`CREATE UNIQUE INDEX ... WHERE del_flag = 0`）。MySQL 没有部分索引，这是第 1 类问题（见 `shared/workflow.md` 第 2 步），推荐方案是：`del_flag` 删除时写入该行的 `id`（未删除为 0），唯一索引建在 `(业务列, del_flag)` 上；另一种是生成列方案。选定后把 `del_flag` 的取值说明同步改到第 3 节。
- MySQL 项目代码里没有外键约束的，问用户是否保留"必须声明外键约束"；不保留时改成"必须为关联字段建索引，关联完整性由业务层保证"。
- SQLAlchemy 用 `MetaData(naming_convention=...)`；其他 ORM 没有统一配置时，规定在迁移脚本里按格式手写名字。

## 8. 查询

默认规则：
- **必须**：通过 ORM 或数据访问库访问数据库；**禁止**拼接 SQL 字符串，原生 SQL 必须绑定参数。
- **必须**：列表查询都分页，每页最多 300 条。
- **必须**：加载关联数据用预加载或批量查询，**禁止**在循环里逐条查询（N+1 问题）。
- **禁止**：`SELECT *`，原生 SQL 里列出需要的字段。
- **必须**：一次业务操作放在一个事务里，操作日志也写在同一个事务中。
- **禁止**：在事务里调用 HTTP 接口、发送消息或投递异步任务，事务里只放数据库语句；需要通知外部的，在事务提交后再做，或写进任务表由 worker 执行。
- **必须**：分页查询的 `ORDER BY` 以唯一字段（一般是 `id`）结尾，保证翻页结果确定。
- **禁止**：超过三张表的 join；join 的字段类型必须完全一致，并且有索引。
- **禁止**：页面搜索用左模糊或全模糊（`LIKE '%x'`、`LIKE '%x%'`），需要时用全文检索或搜索引擎。
- **禁止**：`NOT IN (子查询)`，改用 `NOT EXISTS`。
- **禁止**：时间范围查询用 `BETWEEN`，写成 `col >= 起点 AND col < 终点`；整数和日期字段可以用 `BETWEEN`。
- `IN` 列表的元素不超过 1000 个；统计行数用 `count(*)`，**禁止**用 `count(列名)` 或 `count(1)` 代替；涉及多张表的 SQL，每个列名都带表别名。
- **禁止**：存储过程；业务代码里执行 `TRUNCATE`。
- 批量更新或删除按有索引、值唯一的字段（一般是主键）分批执行，推荐每批 1000 行；循环中**禁止**修改 `ORDER BY` 用到的字段。

按技术确定：参数绑定写法（MyBatis 用 `#{}`，**禁止** `${}` 拼接用户输入；JDBC `PreparedStatement`；SQLAlchemy `text()` + 绑定参数）、预加载写法（`selectinload`、JPA `@EntityGraph`、GORM `Preload`）、事务写法（Spring `@Transactional` 放在 Service 方法上）。

## 9. 迁移

默认规则：
- **必须**：表结构只能通过迁移工具修改，**禁止**手工在数据库里执行 DDL。
- **必须**：迁移文件按"<动词>_<对象>"命名，例如 `add_order_paid_time`；自动生成的迁移要人工检查后再提交。
- **必须**：每个迁移都写回退步骤。无法回退的数据迁移可以不写，但要用注释说明原因。
- **禁止**：修改已经合并到主分支的迁移文件，发现问题时新建迁移修正。
- **必须**：结构变更和数据变更分成两个迁移；数据迁移用批量 SQL，不逐行循环。
- **必须**：给已有数据的表新增非空字段时，要么同时提供默认值，要么分三步：先加可空字段 → 回填数据 → 再改成非空。默认值只能是常量；默认值是 `now()` 这类函数时，按三步处理。
- **禁止**：在迁移里直接重命名已经上线的表或字段。字段改名只改应用层的映射名；必须改库里的名字时，按"新建字段 → 同时写入 → 回填 → 切换读取 → 删除旧字段"分多次发布完成。
- **必须**：删除字段分两次发布：第一次让代码不再读写这个字段，下一次发布才在迁移里删除它。删除表同理，表上的外键在删表前用单独的迁移删除。
- **必须**：部署时执行的结构迁移不超过 3 分钟；超过的数据迁移改成后台分批任务。后台数据迁移任务必须能重复执行而不破坏数据，并且不引用应用的模型代码。
- PostgreSQL 的在线变更规则（只写进 PostgreSQL 项目的规范）：
  - **必须**：在已有表上建索引用 `CREATE INDEX CONCURRENTLY`，删除索引用 `DROP INDEX CONCURRENTLY`；同一个迁移里新建的表除外。含 `CONCURRENTLY` 的语句不能在事务里执行，这样的迁移文件只写这一条语句，并关闭迁移工具的事务包装。
  - **必须**：给已有表加唯一约束时，先用 `CONCURRENTLY` 建唯一索引，再 `ADD CONSTRAINT uk_xxx UNIQUE USING INDEX`；**禁止**直接 `ADD CONSTRAINT ... UNIQUE`。部分唯一索引不能挂成约束，只保留索引。
  - **必须**：给已有表加外键或 `CHECK` 约束时，先 `ADD CONSTRAINT ... NOT VALID`，再在另一个迁移里 `VALIDATE CONSTRAINT`。一个迁移最多新增一个外键；外键列的索引在外键之前创建。
  - **必须**：给已有字段加 `NOT NULL` 时，先加 `CHECK (col IS NOT NULL) NOT VALID`，回填后 `VALIDATE`，最后 `SET NOT NULL`。
  - **禁止**：直接 `ALTER COLUMN ... TYPE` 改字段类型。只有不重写表的改法可以直接做（`varchar` 改 `text`、`varchar(n)` 改长）；其他改法（如 `integer` 改 `bigint`）按"新建字段 → 回填 → 切换 → 删除旧字段"处理。
  - **必须**：每个迁移开头设置 `SET lock_timeout = '1s'` 和 `SET statement_timeout = '5s'`（数值按项目调整），拿不到锁时失败重试，不长时间阻塞线上读写。
  - **必须**：迁移语句能重复执行：建对象用 `IF NOT EXISTS`，删对象用 `IF EXISTS`，或者整个迁移在一个事务里执行。

按技术确定：迁移工具和生成命令（Alembic `alembic revision --autogenerate -m`；Flyway 文件名 `V<版本>__<动词>_<对象>.sql`；Liquibase changeSet；golang-migrate `migrate create -ext sql -dir migrations <名称>`；Prisma `prisma migrate dev --name`）。Flyway 社区版不执行 undo 脚本，回退步骤写在迁移文件末尾的注释里，回退时人工执行。

## 10. 环境与库名

默认规则：
- 库名格式为 `<项目>_<环境>`，环境取 `dev`、`test`、`prod`。**禁止**生产环境连接 `_dev` 或 `_test` 库。
- 集成测试使用独立的 `<项目>_test` 库，每次测试运行前重建。

按技术确定：项目名（用小写 snake_case）；MySQL 里库名即 schema 名；已有库名不符合格式的，保留已有库名并问用户是否只约束新环境。

## 11. 种子数据

默认规则：
- **必须**：预置数据（初始管理员、内置角色和权限、字典项）只能通过种子数据机制写入，**禁止**写进迁移。迁移只负责结构变更和对已有数据的修正。按环境变化的数据（例如初始管理员账号）从环境变量读取，不写死在代码里。
- **必须**：每个需要预置数据的功能单独一个种子模块，返回本次插入的条数，按依赖顺序注册。
- **必须**：种子数据缺了才插入，已有就不动：按业务键判断是否已存在，已存在就跳过；**禁止**更新或删除已有记录，因为线上人工修改过的数据必须保留；修正已有数据走迁移。
- **必须**：每个种子模块都有集成测试，在空库和已有数据的库上各执行两次，第二次插入 0 条且数据与第一次一致。
- **必须**：服务启动时先执行迁移，再执行种子数据。
- 用表格维护种子数据清单："模块 | 内容 | 判断已存在的依据 | 来源"，新增时同步更新。

按技术确定：种子模块的目录和注册方式（Spring 用 `ApplicationRunner`；Python 用 `app/seeds/` + 命令行入口；Go 用 `cmd/seed`）；Flyway 的 repeatable 迁移不能用来写种子数据（它会在内容变化时重复执行）。

## 12. 备份与恢复

默认规则（时间、保留份数直接用这里的默认值；存放位置和执行方式由用户提供，没给时写占位）：
- **全量备份**：每天定时（默认 03:00，时区 `Asia/Shanghai`）做一次全量备份，文件名为 `<库名>_<YYYYMMDD_HHMMSS>_<原因>.<扩展名>`，原因为 `daily`（定时）、`pre-migrate`（迁移前）、`manual`（手动）。先写临时文件，成功后再改名，失败时不留下半个备份。
- **保留周期**：`daily` 保留最新 7 份，另外保留最近 4 个周日各自最新的一份；`pre-migrate`、`manual` 保留 30 天。文件名不符合格式的文件不动。
- **迁移前备份**：服务启动时发现有待执行的迁移，先做全量备份，备份成功后才执行迁移；备份失败则服务不启动。空库首次部署不备份。
- **附件**（项目有文件存储时）：附件每天同步到备份目录，只增不删；**禁止**给附件配置过期规则或写清理附件的定时任务。
- **存放位置**：写明备份目录；备份和数据库在同一台机器同一块盘上时，在规范里明确标出这是风险，并写出异地存放的待办。
- **恢复演练**：修改备份脚本后、上线前，都要完整演练一次"备份 → 删库 → 恢复 → 校验行数"，在本节记录日期、环境、步骤和结果。
- **恢复步骤**：按顺序写出停服务、重建库、恢复、校验（迁移版本和各表行数）、启动服务的命令。
