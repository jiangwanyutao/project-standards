# 开发流程规范默认规则

每章分两部分：

- **默认规则**：与技术无关，按原意写进规范。
- **按技术确定**：要从仓库推断或问用户的项，括号里是空项目时的推荐值。

## 1. 分支

默认规则：
- 主分支始终可以发布。**禁止**直接向主分支推送，改动一律经过合并请求进入主分支。
- 功能分支从主分支最新的提交拉出，命名为 `<type>/<简短英文描述>`，type 与提交说明的 type 相同，例如 `feat/order-cancel`、`fix/login-timeout`。
- 一个分支只做一件事，合并后删除。分支存在超过一周的，先把主分支的最新改动合进来再继续。

按技术确定：主分支名（看仓库现有分支，空项目推荐 `main`）；代码托管平台上的分支保护设置写进汇报，规范里只写规则。

## 2. 提交说明

默认规则：
- 格式为 `<type>: <描述>`，type 取下表中的一个：

  | type | 用于 |
  |---|---|
  | feat | 新功能 |
  | fix | 修复缺陷 |
  | refactor | 不改变行为的代码调整 |
  | perf | 性能优化 |
  | docs | 只改文档 |
  | test | 只改测试 |
  | chore | 依赖、构建配置、脚本等杂项 |
  | ci | CI 配置 |

- 描述写清楚改了什么，例如 `fix: 取消已支付的订单时返回 409`。**禁止**写"修改代码""更新"这类看不出改了什么的描述。
- 一个提交只做一件事；格式化、重命名这类大范围机械改动单独提交。
- 有不兼容改动（接口字段删除或改名、配置项改名）时，在 type 后加 `!`，例如 `feat!: 订单接口的 amount 改为分为单位`，并在正文里写明调用方要怎么改。

按技术确定：描述的语言（看 `git log`，空项目推荐中文，type 保留英文）；历史提交已有统一格式（例如 `feat(order): ...`）时沿用。

## 3. 合并请求

默认规则：
- 合并请求的描述按下面的模板填写：

  ```markdown
  ## 改了什么
  <一两句话>

  ## 为什么改
  <需求、缺陷编号或原因>

  ## 怎么验证的
  <跑了哪些测试；改界面的附截图>

  ## 需要注意
  <迁移、配置项变化、不兼容改动；没有就写"无">
  ```

- **必须**：至少 1 名作者以外的成员批准后才能合并，作者**禁止**批准自己的合并请求。
- 一个合并请求的改动建议不超过 400 行，超过的拆成几个依次合并。**例外**：生成文件（接口类型、锁文件）和迁移文件不计入。
- 评审时逐项看：
  - 是否违反各规范里标"必须""禁止"的条目；
  - 新增或改变的行为有没有对应的测试；
  - 数据库迁移是否符合数据库规范的迁移一章；
  - 接口改动是否同步更新了前端接口类型和接口文档；
  - 代码、配置、日志里有没有密码、密钥、token；
  - 新增的运行时依赖是否已登记到技术选型规范。
- 评审意见分两种：必须改的直接写；只是建议的以"建议："开头，作者可以不改。作者改完后由提出意见的人确认。
- 合并方式用 squash 合并，合并后的提交说明按第 2 章的格式写。

按技术确定：评审人数（团队只有一两个人时，用户可以改为"作者自查后合并"，汇报里说明）；合并方式（仓库历史里全是 merge 提交的沿用 merge）。

## 4. 合并前检查

默认规则：
- **必须**：合并前通过后端规范第 1 章、前端规范第 1 章的质量门禁，任何一项失败都禁止合并。本文不重复写命令，写出各自在哪个目录执行。
- 有 CI 时，质量门禁在 CI 里对每个合并请求执行，CI 不通过的合并请求不能合并；写出 CI 配置文件的位置。没有 CI 时，作者在合并请求的"怎么验证的"里贴出本地执行门禁的结果。
- **禁止**：为了让 CI 通过而跳过测试、调低覆盖率要求或删掉检查项，确实需要调整的单独提合并请求说明原因。

按技术确定：CI 配置文件的位置（看仓库现有配置；空项目按代码托管平台确定，GitHub 用 `.github/workflows/ci.yml`，GitLab 用 `.gitlab-ci.yml`，平台未知时写占位 `<CI 配置文件>`，并列为需要用户补充的取值）。

## 5. 版本号与 CHANGELOG

默认规则：
- 版本号按 `主版本.次版本.修订号`：有不兼容改动时升主版本，新增功能升次版本，只修缺陷升修订号。
- 每次发布在主分支上打标签 `v<版本号>`，例如 `v1.4.0`。
- 根目录的 `CHANGELOG.md` 按版本倒序记录面向使用者的改动，每个版本下按"新增、修改、修复、删除"分组；还没发布的改动写在最上面的"未发布"一节下。
- **必须**：合并请求有使用者能感知的变化时，同时在 `CHANGELOG.md` 的"未发布"下加一行；只改内部实现、测试、文档的不加。
- 发布时把"未发布"一节改成 `## <版本号>（<日期>）`。

按技术确定：版本号写在哪个文件（`pom.xml`、`pyproject.toml`、`package.json`，前后端各自有版本时分别写明）；部署和发布的具体步骤属于部署方式，由用户提供，用户没给时写占位 `<发布步骤>`。
