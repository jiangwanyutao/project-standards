# 技术选型规范默认规则

每章分两部分：

- **默认规则**：与技术无关，按原意写进规范。
- **按技术确定**：要从代码推断或问用户的项，括号里是空项目时的推荐值。

## 1. 选型总表

默认规则：
- 用一张表写出每一层的选择，列固定为：

  | 层 | 选择 | 版本 | 选择理由 | 依据 |
  |---|---|---|---|---|
  | 后端语言 | Java | 17 | 团队熟悉，长期支持版本 | 用户指定 |
  | 后端框架 | Spring Boot | 3.x | …… | `backend/pom.xml` |

- 行按下面的顺序排列，项目里没有的层删掉：
  - 后端：语言、框架、构建与依赖管理、ORM 或数据访问库、数据库、迁移工具、日志库、配置库、测试框架、格式化与 lint 工具。
  - 前端：框架、语言、构建工具、包管理工具、样式方案、组件库、图标库、路由、服务端状态、测试框架、lint 与格式化工具。
  - 本地环境：运行时（JDK、Python、Go、Node.js）、Docker 等需要开发者自己安装的工具。
- "版本"写主版本号，例如 `17`、`3.x`。有锁文件的项目，锁文件就是精确版本的出处，本文不重复写次版本和修订号。
- "选择理由"每行一句话，写这个项目为什么用它，例如"组件库自带表格、表单、弹窗，适合后台管理页面"。**禁止**写"业界主流""性能优秀"这类放到哪个库上都成立的话。
- 表格下面写一句："本表以外的运行时依赖，引入前按第 2 章登记。"

按技术确定：
- 每一行的选择和版本：有代码时从依赖文件和锁文件读；空项目用用户给的选型，用户没给版本的，用当时最新的长期支持版本或稳定主版本，并在汇报的"使用的推荐值"一节列出。
- 用户没指定、各规范需要用到的工具，推荐值取自对应规范的 `references/defaults.md`（例如后端格式化工具见 backend-standard，组件库见 frontend-standard），本文只登记，不另定。

## 2. 引入与升级依赖

默认规则：
- **必须**：引入新的运行时依赖前，先在选型总表里加一行，写明用途和理由，和代码放在同一个合并请求里。只在开发和测试时用的依赖（测试工具、lint 插件）不登记。
- **禁止**：同一种用途同时用两个库，例如两个日期库、两套请求封装、两个图标库、两个组件库。确实要换库时，先在本表把新库写上、旧库标"迁移中"，迁移完成后删掉旧库那一行。
- **必须**：能用已有依赖或语言标准库完成的，不引入新依赖。
- **必须**：升级主版本（例如 Spring Boot 3 升 4、React 18 升 19）单独提一个合并请求，先改本表的版本，合并请求里写明不兼容的改动和验证方式。
- 次版本和修订号的升级随时可以做，跑通质量门禁即可合并。
- **禁止**：引入许可证不在下面清单里的依赖，清单外的先问负责人。

  | 允许的许可证 |
  |---|
  | MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC |

按技术确定：项目是开源项目或对许可证另有要求时，按用户说的改写许可证清单。

## 3. 选择依据

默认规则：
- 写出引入新依赖时要检查的几条，每条一行，评审时逐条看：
  - 近 12 个月内有发布新版本；
  - 没有未修复的高危漏洞（用后端、前端规范质量门禁里的漏洞扫描命令检查）；
  - 许可证在第 2 章的清单内；
  - 和选型总表里已有的库不重复。
